# internal/upstream/eea

Ingests Bulgaria's 32 official ИАОС/ExEA reference stations, published through
the European Environment Agency, as a second station layer alongside the
sensor.community devices the rest of this repo collects.

## Where the data comes from

The government's own portal is not a usable source. Its map calls
`GET https://eea.government.bg/kav/ajax/getStationsForMapJson?hours=N`, which
on 2026-09-09 returned all 32 stations with coordinates, Bulgarian names,
addresses and station types — and `value: 0`, empty `componentName`, empty
`dt` for every one of them. The per-station endpoint `getStationDataJson`
returned a zero-length body. That server also presents an incomplete TLS
chain (leaf certificate only, no Sectigo intermediate), so any client of it
needs an explicit CA bundle just to connect, on top of the data being empty.

The same stations reach us through the EEA Air Quality Download API instead,
which is live and about one hour behind:

| | |
|---|---|
| URL list | `POST https://eeadmz1-downloads-api-appservice.azurewebsites.net/ParquetFile/urls` |
| body | `{"countries":["BG"],"cities":[],"pollutants":[],"dataset":1,"source":"API"}` |
| dataset 1 | UTD — unverified, near-real-time (see `datasetUTD` in client.go) |
| result | ~141 sampling points over 32 stations, ~717 KB each, ~99 MB total |
| format | Parquet, snappy, 3 row groups of 5000 rows |
| columns read | `Samplingpoint, Pollutant, Start, End, Value, Unit, AggType, Validity, Verification` |
| readings | hourly means in `ug.m-3` or `mg.m-3`, history back to 2025-01-01 |

## Coordinates: a separate, frozen file

The download API carries no coordinates. They come from
`https://discomap.eea.europa.eu/map/fme/metadata/PanEuropean_metadata.csv`
(26 MB, tab-delimited despite the `.csv` extension, last modified
2024-03-11), which carries `SamplingPoint`, `AirQualityStationEoICode`,
`Longitude`, `Latitude`, `AirQualityStationType` and `AirQualityStationArea`.
All 141 current sampling points resolve in it, but the file is frozen: a
station commissioned after March 2024 would arrive without coordinates. The
collector logs and counts (`Stats.Unplaceable`) such a sampling point rather
than guess at a position — see `Collector.RunOnce` in collector.go.

`ParseMetadata` (metadata.go) keys each row `<Countrycode>/<SamplingPoint>`
because that is the exact format the download API's own `Samplingpoint`
field uses (e.g. `BG/SPO-BG0070A_06001_100`); the metadata file's own
`SamplingPoint` column lacks the country prefix.

## Station names

The metadata CSV has no human-readable name column — only
`AirQualityStationNatCode`, a short internal code (`Vd3`), not a name a
reader would recognise. The Bulgarian names, addresses and government
classification come from `bg_station_names.json`, a committed, build-time
join table (embedded via `//go:embed`, see names.go), keyed by
`AirQualityStationEoICode`.

That table was built once against the government portal's own JSON (the same
`getStationsForMapJson` endpoint above, which does carry names even though
its `value` fields are broken) and verified: all 32 live EoI codes resolve,
every one matches within 0 metres of the download API's own coordinates, and
the join is one-to-one both ways. It has no runtime dependency on
`eea.government.bg` — the broken-TLS host never needs to be a production
dependency. `applyBGStationName` in names.go overwrites `Station.Name` at
upsert time; a station absent from the table (anything added since the table
was built) keeps its national code instead of going blank.

Cost if this table goes stale: a renamed or recommissioned station shows an
old name until the table is regenerated by hand. The EoI codes themselves are
stable, so this degrades gracefully rather than breaking the join.

## Pollutant codes

`pollutant.go`'s `metricForCode` carries the eight codes this feed maps onto
canonical metric names; every other code the API returns is ignored
(`MetricFor` returns `false`):

| EEA code | Metric | Note |
|---|---|---|
| 1 | SO2 | |
| 5 | P1 | PM10, shares sensor.community's name |
| 6001 | P2 | PM2.5, shares sensor.community's name |
| 7 | O3 | |
| 8 | NO2 | |
| 9 | NOX | NOx as NO2 |
| 10 | CO | arrives in `mg.m-3`, scaled ×1000 by `NormaliseValue` |
| 20 | C6H6 | benzene |

Coverage across the 32 Bulgarian stations, in sampling points: SO2 28, PM10
27, NO2 25, O3 20, CO 18, benzene 18, PM2.5 4, NOx-as-NO2 1. PM2.5 — the
site's default metric — exists at only 4 of 32 stations, so the official
layer looks nearly empty on PM2.5 until the reader switches to PM10.

## The `Validity` vocabulary

Every row carries EEA's own `Validity` flag. This package maps it onto the
existing `quality` column rather than adding a new one:

- `Validity > 0` → stored with quality `"ok"`.
- `Validity <= 0` → stored with quality `"source_invalid"` — kept, not
  dropped, so a rejected hour is visible as a gap rather than indistinguishable
  from a station that reported nothing at all.

`usableQuality` in `internal/store/aggregate.go` is `{"ok", "no_neighbours"}`
and is deliberately left unchanged: `"source_invalid"` rows are stored but
never averaged.

## Operational notes

- `Client.FetchFile` uses conditional `GET` with `If-Modified-Since`; an
  unchanged file costs a 304 and is counted in `Stats.Unmodified`.
- Every HTTP read is bounded by `io.LimitReader` against
  `config.EEA.MaxPayloadBytes` — see client.go. The metadata file alone is
  26 MB, so that bound must be sized for it (`internal/config/validate.go`
  checks the block is internally consistent, not that it is large enough for
  this specific file).
- In memory, the metadata file is refetched only every `MetadataInterval`
  (weekly is generous for a file untouched since 2024-03-01); a failed
  refresh keeps the previously loaded copy rather than running with no
  official layer at all.
- On disk, `Client.FetchMetadata` writes the raw CSV to `MetadataCache` after
  every successful fetch. `Collector.loadMetadata` reads that file back only
  as a last resort — on startup, when there is no in-memory copy yet and the
  live fetch also failed — so a process restart during an upstream outage
  still has coordinates to place stations with.
- `Client.FileURLs` only follows a returned URL whose scheme and host match
  the configured `EEA.URL`; anything else is refused and counted in
  `Stats.UntrustedURL` rather than followed. The `/ParquetFile/urls` response
  is third-party input, so `Client.FetchFile` must never be steered at an
  arbitrary host by it.
- `Collector.RunOnce` writes readings in chunks of `writeChunkSize` (2000)
  rather than one `pgx.Batch` for the whole cycle — history backfills alone
  can put ~2M readings through a single run. Each chunk is a separate
  `WriteStationReadings` call, so a failure partway through a cycle leaves
  earlier chunks durably written instead of rolling the whole cycle back.
