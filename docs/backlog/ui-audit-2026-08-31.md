# Web UI audit — 2026-08-31

Browsed the running app at `https://airbg.org` from the LAN (Chromium via Playwright),
desktop 1440×900 and 2304×1323, mobile 390×844. Screenshots in `.playwright-mcp/`.

## The single most useful fact

The whole application ships **74 lines of hand-written CSS**:

| File | Lines |
|---|---|
| `internal/web/static/theme.css` | 15 |
| `internal/web/static/app.css` | 59 |

Everything else on screen is browser default — `fieldset`/`legend` chrome around the metric
switcher, native `button` styling, unstyled `ul`, default link blue-turned-green. So "the
design needs a lot of improvement" is not a matter of polishing an existing style; there is
no design system to polish. That is good news: nothing has to be unpicked.

## How this audit held up

Every finding below was re-checked against the running site before anything was written.
Three of six survived: **F3** (a real defect, fixed), **F4** and **F5** (real, fixed).
**F1** and **F2** were refuted outright and **F6** was misdiagnosed — all three because the
original pass described the screen rather than measuring it.

Treat the design findings (D1–D6) the same way: they are impressions until measured.

## Functional defects

### F1 — Map canvas does not fill its container — **REFUTED, not a defect**
The original measurement was mine and it was wrong. `app.css:3` sets
`header, main, footer { max-width: 60rem; padding: 1rem }`, so the content column is
60rem − 2rem = **928 px** — exactly the width I had recorded as the defect. Live
measurement confirms the map tracks its container: canvas 926 in container 928 at a
1440 px viewport, and 356 in 358 after resizing to 390 px *without a reload*. MapLibre
handles window resize itself; no `ResizeObserver` is needed.

The 655 px figure was taken at a narrower viewport than the one recorded beside it.

What survives is a design complaint, not a functional one, and moved to D2/D3: the map is
confined to a prose measure and a fixed 24rem height.

### F2 — The map never fits Bulgaria — **REFUTED, not a defect**
Both halves of the original claim were wrong, and both were wrong because I described the
screen instead of measuring it.

**The country does fit.** At `data-zoom=7` in the live 926×382 canvas, Web Mercator gives
10.17° of longitude against Bulgaria's 6.25°, and a Mercator span of 0.0732 against the
country's 0.0708. Nothing is cut off. The latitude margin is only 3.4 % (~6 px top and
bottom), so the fit survives on the fixed 24rem height — worth stating in D2/D3 before that
height changes, but it is not a defect today.

**Geolocation does not move it either.** `/api/v1/locate` returns
`{"source":"default","lon":25.4858,"lat":42.7339,"zoom":7}`, and `applyLocate`
(`web/src/lib/locate.js:7`) moves the map only for `source == "geoip"`. The cold load stays
on the configured national view.

**The "seven dots" were miscounted.** `/api/v1/overview` returns 28 oblasti, 20 of them
covered with a P2 value. Zoom 7 is the country tier, so those dots are area centroids, not
sensors — which is the choropleth design working, not sensors going missing.

Nothing to implement. The saved-view/geolocation/country-fit precedence that was proposed
as the fix has no defect to fix.

### F3 — The area series never aggregates — **root-caused and fixed**
`/area/sofiya-grad-oblast` rendered a dense spike field under the title
"ПМ2.5, последните 24 часа". The label was honest: the window really was 24h, and only
~4 hours of readings existed. The endpoint self-reported the defect —
`hourly: false`, **12 333 points, 12 333 distinct timestamps, 388 KB**.

Cause: `areaRawSeriesSQL` grouped on `r.time`. Sensors report asynchronously at second
resolution, so equality on a raw timestamp almost never matches two rows and every
`avg()` averaged a single sensor. `allAreaRawSeriesSQL` — which feeds the snapshot that
actually serves the default metric and period — carried the identical defect.

Every existing test seeded its sensors at the *same instant*, which is why a query that
aggregated nothing in production had passing tests.

Fixed by bucketing (`time_bucket`) with a per-period `bucket:` width in `airbg.yaml`.
A 388 KB unauthenticated `GET` of raw readings for the country's largest area was also
bulk extraction; 24h now returns 288 points.

### F4 — Placeholder text shipped under the chart — **root-caused and fixed**
Not our markup: it is uPlot's built-in legend, which *is* the hover readout. `Chart.svelte`
passed no `legend` option, so uPlot rendered its default — the label beside an em-dash — with
no cursor on the plot. `legend: {show: false}` would have taken the readout away with it, so
a `setCursor` hook now gates the legend's visibility on `cursor.idx != null` (not a truthy
test: index 0 is the leftmost point of every chart).

Near-miss worth keeping: the first version's CSS was scoped, and Svelte pruned it as an
"Unused CSS selector" because `chart-live` is added at runtime and never appears in the
template. It would have shipped, passed its test, and done nothing. Both selectors are
`:global` now, and the built chunk was verified on the live site.

Residual: `Time` is still uPlot's own English default label. Visible only on hover now, but
still English on a Bulgarian page — needs a catalogue string, so it goes with D2's copy work.

### F5 — `favicon.ico` 404s — **fixed**
Confirmed nothing was served and no `<link rel="icon">` was rendered at all. Added
`internal/web/static/favicon.svg` and declared it in `base.gohtml`. `/favicon.ico` still 404s
by design: a browser stops guessing that path once the document names an icon.

### F6 — Sensor counts and map dots disagree — **not a data bug; a copy gap**
Checked the endpoints. `/api/v1/area/sofiya-grad-oblast/sensors` returns **585** sensors, so
nothing is being dropped. The area page opens at `data-zoom="9"` and `data-zoom-sensor="11"`,
so `tierFor` puts it on the *city* tier: the ~25 dots are Sofia's neighbourhood aggregates,
not sensors.

That tiering is the anti-enumeration design and must stay. The defect is that the reader is
never told: `refresh` (`map.js:224`) shows the "zoom in" hint only when the sensor tier is
refused for want of a slug, and on an area page the slug is set — so the page prints
"568 сензора" beside 25 dots and explains neither number.

Fix is copy plus a hint condition, not a query change. Belongs with D2 (the map has no
legend and no tier explanation).

## Design defects

### D1 — No visual identity at all
Native form controls, no type scale, no spacing scale, no colour system beyond the green
link colour. The metric switcher is a literal `fieldset` with a `legend` reading
"Показател".

### D2 — The colour key is unexplained
Dots are green / teal / yellow / grey. No legend anywhere. Grey in particular reads as
"broken" rather than "no recent data". The app has `web/src/lib/colour.js` and an
`/api/v1/scales` endpoint, so the scale is defined in code but never shown to the reader.

### D3 — The areas list is a directory, not a dashboard
28 rows, each a name plus a sensor count. No value, no colour, no ranking, no sparkline.
"Недостатъчно данни за този район" appears eight times in orange, which reads as eight
errors rather than as a normal state.

### D4 — Layout widths are inconsistent
Text column, map and chart each have a different width, so nothing lines up down the page.

### D5 — Header does not survive mobile
At 390 px the wordmark wraps to two lines and "Български" / "English" split across lines.
The current-language indicator is bare text next to a link, with no shared styling.

### D6 — Footer weight
Four stacked legal paragraphs, all at body weight, taking as much vertical space as a
content section.

## What was verified as working

- Bulgarian ↔ English switching present in the header; page titles localised
  ("София-град — Мръсен въздух").
- Basemap loads from the self-hosted PMTiles archive (`206 Partial Content` range requests)
  with glyphs; CSP is not blocking anything.
- `/api/v1/scales`, `/api/v1/overview`, `/api/v1/locate` all 200.
- Area pages render per-area data and are linked from the home list.
- Attribution present for sensor data, boundaries and basemap; the "indicative, not a
  reference method" caveat is on every page.
